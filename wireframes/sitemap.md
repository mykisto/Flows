# Flows - Sitemap (draft)

The bridge from jobs to wireframes. Built on [`personas.md`](../research/personas.md), [`jtbd.md`](../research/jtbd.md), and [`research.md`](../research/research.md). This file starts with the **entity inventory** - the objects a person deals with to close their jobs - *before* any screen or navigation is drawn. Screens and flows come in later sections, not here.

**Method.** Every entity is traced to a specific job from [`jtbd.md`](../research/jtbd.md) (Main / RJ1-RJ5 / EJ1-EJ3). An object that no in-scope job requires goes to **Under question**, not the main list. An object whose existence is only inferred is marked `[?]`. Nothing is added because it is conventional in a finance app; if the jobs do not call for it, it is not here.

**Job index (from jtbd.md).** Main = whole position + income, no upkeep · RJ1 = bring the numbers together · RJ2 = hold everything I own · RJ3 = income coming + arrived · RJ4 = move in without redoing work · RJ5 = decide how much to share · EJ1 = feel on top · EJ2 = feel my data is mine · EJ3 = feel my plan is working.

## Entities

### E1 - Holding (the spine)
A single asset position the user owns. The central object; every other entity hangs off it or rolls it up.

- **Parts.** Asset name · asset type (→ E2) · quantity · cost basis · current value + its "as of" freshness · native currency (→ E7) · valuation class (price-tracked vs manually-valued) · symbol/ISIN key (price-tracked only) · income info (→ E3) · **custom fields** (the free-form escape hatch when a type does not fit).
- **Spawned by.** **RJ2** ("record it anyway ... so I do not fall back to a spreadsheet for the parts that do not fit"). The custom-fields part is RJ2's 90%→100% escape hatch (research §2 mechanism 2). Underpins the **Main job** - there is no consolidated position without holdings.
- **Related to.** Is-of one **Asset type** (E2); carries an **Income schedule** (E3); accumulates **Value snapshots** (E5); rolls up into the **Portfolio summary** (E6); valued in a **Currency** (E7); can be produced by an **Import draft** (E8).

### E2 - Asset type (typed stub)
A pre-structured template per asset class that knows its own fields, units, and income shape. v1: REIT/fund certificate (Inzhur), OVDP, stock/ETF, crypto, real estate, deposit.

- **Parts.** Type name · the default fields it carries (a bond stub → coupon + maturity; a dividend stock → frequency; a deposit → interest + term) · valuation class it implies (price-tracked vs manual).
- **Spawned by.** **RJ2** - typed stubs cover the common ~90% correctly so the user is not building schema by hand (research §2 mechanism 1). Type also decides how E5 and the 30-day direction behave (decision: price-tracked vs manually-valued split).
- **Related to.** Classifies each **Holding** (E1); shapes that holding's **Income schedule** (E3) and its valuation path (E5).

### E3 - Income schedule
The recurring-income definition attached to a holding: what it pays and when. Essential, not optional - it powers the cash-flow view.

- **Parts.** Amount per payout · cadence/frequency (monthly dividend · coupon date · rent · deposit interest) · next date(s) · currency.
- **Spawned by.** **RJ3** ("see what is coming ... across all of them"). It is the rule that **generates** the forward payouts the user actually looks at.
- **Related to.** Belongs to a **Holding** (E1); its shape comes from the **Asset type** (E2); **generates Payouts** (E4).

### E4 - Payout (income event)
One instance of income, projected or realized. The unit the payout calendar and the realized track record are both made of.

- **Parts.** Source holding · amount · currency · date · **status** (projected → due-to-confirm → realized) · confirm/edit action.
- **Spawned by.** **RJ3** (forward: "what is coming") and **EJ3** (realized: "the income I have actually earned add up"). The status flow is the auto-roll: a projected payout flips to *due-to-confirm* once its date passes, for one-tap confirm/edit (decision: realized = auto-roll + one-tap).
- **Related to.** Generated by an **Income schedule** (E3); belongs to a **Holding** (E1); aggregated into the **Portfolio summary's** blended/forward income (E6).

### E5 - Value snapshot (valuation history)
A recorded value of a holding at a point in time. The real-data basis for the 30-day change and direction.

- **Parts.** Holding · value · currency · as-of timestamp · source (auto-fetched vs user-entered).
- **Spawned by.** **Main job** (position + its direction) and **EJ1** (feel on top, not unsure). For price-tracked holdings the history is auto-fetched; for manually-valued ones the user enters periodic updates, each saved as a snapshot. Direction is shown **only where real snapshots exist**, never fabricated (decision: 30-day change only where real data).
- **Related to.** Accumulates under a **Holding** (E1); feeds the position figure and direction in the **Portfolio summary** (E6); for price-tracked holdings, filled by the price feed (see Under question, U1).

### E6 - Portfolio summary (derived aggregate)
The consolidated whole the user opens Flows to see. **Computed, not stored** - a roll-up of E1/E4/E5, listed as an entity because it is the object the Main job centers on.

- **Parts.** Total position (sum of current values in display currency) · breakdown by asset type · blended this-month income (realized + projected) · upcoming projected income. (How these split into lenses/screens is a later section, not decided here.)
- **Spawned by.** **Main job** ("understand my whole position and what it is paying me") and **EJ1**. The co-equal position + income framing comes straight from the research (§6 move #1: upkeep/consolidation is the named pain, forward income a latent delight).
- **Related to.** Aggregates **Holdings** (E1), **Payouts** (E4), and **Value snapshots** (E5); rendered in the user's **display Currency** (E7).

### E7 - Currency & FX
Multi-currency holdings shown in one chosen display currency, with the native value kept visible. A design theme, not a footnote (Inzhur values in UAH pegged to USD; users also hold other currencies).

- **Parts.** Native currency per holding/payout (a field on E1/E4) · the user's single **display-currency** choice · the **daily FX rate** (auto-fetched) · native + converted shown together.
- **Spawned by.** **Main job** - "whole position" across several currencies is impossible without one display currency; multi-currency clarity is a confirmed beachhead want (research §6: R8, UAH/USD peg). Daily-fetched FX keeps a fresh price from pairing with a stale rate (decision: FX daily, not live-tick).
- **Related to.** A field on **Holding** (E1) and **Payout** (E4); the display choice scales the whole **Portfolio summary** (E6).

### E8 - Import draft & mapping
The bring-over from the user's existing spreadsheet: the column mapping plus the draft rows awaiting review. The bridge that removes Excel switching cost.

- **Parts.** Source file (CSV/sheet now; PDF/image later) · auto-detected header→field mapping · user remap overrides · saveable mapping template · parsed **draft holdings** pending review/confirm before they become real E1 holdings.
- **Spawned by.** **RJ4** ("bring it across without re-entering everything"). Auto-detect + remap is the CSV bridge (decision: CSV = auto-detect + remap). An **optional** AI-assisted variant drafts the mapping from a messy file (needs the BYOK credential, U2).
- **Related to.** Produces **Holdings** (E1); its optional AI path depends on the BYOK LLM credential (U2).

### E9 - Privacy / sharing stance
Where the user sits on the privacy↔convenience line. Local-first by default, but a stance the user picks, not a single dogma.

- **Parts.** Default = local-first, no account, "never your balances" · per-portion sharing choice (which holdings stay local vs shared) · governs any opt-in sync if enabled (U3).
- **Spawned by.** **RJ5** ("choose what stays on my device and what I share") and **EJ2** ("feel my data is mine"). Honest caveat carried from the research: 0% name distrust as the top pain and 50% are comfortable with bank/broker apps, so this is a selectable stance and acquisition story, not a hero (research §7.3).
- **Related to.** Pairs with the opt-in **Account / User** (E10) as the opposite pole of the same spectrum; governs which **Holdings** (E1) are shared vs local.

### E10 - Account / User (optional identity)
The opt-in identity for a user who chooses the automation end of the spectrum over local-only. It exists **only when the user opts in** - local-first / no-account stays the default, so Flows does not become the cloud-account-by-default tracker it differentiates against.

- **Parts.** A user identity/credential · the sharing scope it carries (which holdings are shared vs kept local, with E9) · one or more **broker sync connections** (e.g. Interactive Brokers) that auto-pull a holdings list · the data sync writes back (new/updated holdings).
- **Spawned by.** **RJ5** - its convenience pole ("opt into broker sync for part of the portfolio while keeping the rest local"; half the surveyed users are comfortable with bank/broker apps). Serves **RJ1** for the syncable subset by bringing those numbers together automatically.
- **Related to.** Opposite pole of the **Privacy / sharing stance** (E9); **auto-creates Holdings** (E1) via sync; gated by the user's stance.
- **Beachhead caveat (from jtbd).** Broker sync reaches no Ukrainian institutions, so for the Inzhur beachhead it closes no reachable job and the UA core (Inzhur + OVDP) is fed by its own feeds, not by sync. Account + sync therefore serve the non-UA long tail and future expansion; they are opt-in and **off the beachhead critical path** - they should not drive the core screens or the usability test. (Open technical question, deliberately unsettled: whether opt-in sync truly needs a server account or can stay a client-side broker connection.)

## Under question

Objects deliberately kept out of the main list - either no in-scope job requires them, a job exists but is explicitly deferred, or their existence is only inferred. Named here so the exclusion is a decision, not an oversight.

- **U1 - Price feed / market-data source `[system]`.** Auto-fetched current price + history for price-tracked assets (keyed on symbol), plus the OVDP/Inzhur feeds. **Why not a main entity:** no job makes the *feed itself* something the user handles - they deal with the resulting value and its "as of" freshness (E5), not the feed object. Infrastructure behind RJ1, not a user-facing entity. The research confirms freshness, not feed coverage, is the trust bar (§7.3).
- **U2 - BYOK LLM credential `[conditional]`.** The user's own LLM key (or on-device model) for AI-assisted import. **Why not main:** it exists only on the optional power path of E8; RJ4 is already matched by competitors and is not an unmet job (jtbd conclusion), so this is in scope but not load-bearing. A sub-part of E8, surfaced only if the user opts into AI import.
- **U3 - AI conversation as the primary edit surface `[?] undecided`.** A floated direction: the user adds, removes, connects, disconnects, and edits assets mainly by talking to an AI rather than through forms. **Why not a main entity (yet).** It is undecided, and it is an *interaction model* for mutating E1-E10, not a data object of its own; if it ships and the thread is kept, the stored object would be a conversation / command history (reusing the BYOK credential, U2). **Two tensions to settle before committing:** (a) current scope defers AI beyond import, so making AI the primary create/edit/delete surface is a deliberate expansion, not a default; (b) a chat-first primary surface risks the "faster than my spreadsheet" task - a direct tap can beat composing a sentence. Recorded so the idea is not lost; decide it explicitly, with the usability test in mind. *(Broker sync, formerly listed here, is now modeled under E10.)*
- **U4 - Language preference (EN↔UA) `[constraint, not a job]`.** The in-UI language toggle. **Why not main:** no jtbd job spawns it. It exists for the validation/portfolio need (Ukrainian for the Inzhur usability tests, English for the case study), a project constraint rather than a user job. Real and in v1 scope, but not entity-of-a-job, so it sits here.
- **U5 - Tag / goal `[?]`.** A label or a long-term target on a holding (as in FIREkit). **Why not main:** the only job that would need it is HJ3 ("track progress toward a long-term goal"), which is a hypothesis with no research support. Excluded until testing gives it a basis.

**Default guardrail.** Local-first / no-account stays the **default**; the **Account / User** (E10) is opt-in, never assumed. Keeping it opt-in is the point - the cloud-account-by-default model is exactly what Flows differentiates against, so the account is the exception a user chooses, not the baseline.
