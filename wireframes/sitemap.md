# Flows - Sitemap (draft)

The bridge from jobs to wireframes. Built on [`personas.md`](../research/personas.md), [`jtbd.md`](../research/jtbd.md), and [`research.md`](../research/research.md). This file starts with the **entity inventory** - the objects a person deals with to close their jobs - *before* any screen or navigation is drawn. Screens and flows come in later sections, not here.

**Method.** Every entity is traced to a specific job from [`jtbd.md`](../research/jtbd.md) (Main / RJ1-RJ5 / EJ1-EJ3). An object that no in-scope job requires goes to **Under question**, not the main list. An object whose existence is only inferred is marked `[?]`. Nothing is added because it is conventional in a finance app; if the jobs do not call for it, it is not here.

**Job index (from jtbd.md).** Main = whole position + income, no upkeep · RJ1 = bring the numbers together · RJ2 = hold everything I own · RJ3 = income coming + arrived · RJ4 = move in without redoing work · RJ5 = decide how much to share · EJ1 = feel on top · EJ2 = feel my data is mine · EJ3 = feel my plan is working.

## Entities

### E1 - Holding (the spine)
A single asset position the user owns. The central object; every other entity hangs off it or rolls it up.

- **Parts.** Asset name · asset type (→ E2) · quantity · cost basis · current value + its "as of" freshness · native currency (→ E7) · valuation class (price-tracked vs manually-valued) · symbol/ISIN key (price-tracked only) · income info (→ E3) · **custom fields** (the free-form escape hatch when a type does not fit).
- **Spawned by.** **RJ2** ("record it anyway ... so I do not fall back to a spreadsheet for the parts that do not fit"). The custom-fields part is RJ2's 90%→100% escape hatch (research §2 mechanism 2). Underpins the **Main job** - there is no consolidated position without holdings.
- **Related to.** Is-of one **Asset type** (E2); carries an **Income schedule** (E3); accumulates **Value snapshots** (E5); rolls up into the **Portfolio summary** (E6); valued in a **Currency** (E7); can be produced by an **Import draft** (E8).

### E2 - Asset type (typed stub)
A pre-structured template per asset class that knows its own fields, units, and income shape. v1: REIT/fund certificate (Inzhur), OVDP, stock/ETF, crypto, real estate, deposit.

- **Parts.** Type name · the default fields it carries (a bond stub → coupon + maturity; a dividend stock → frequency; a deposit → interest + term) · valuation class it implies (price-tracked vs manual).
- **Spawned by.** **RJ2** - typed stubs cover the common ~90% correctly so the user is not building schema by hand (research §2 mechanism 1). Type also decides how E5 and the 30-day direction behave (decision: price-tracked vs manually-valued split).
- **Related to.** Classifies each **Holding** (E1); shapes that holding's **Income schedule** (E3) and its valuation path (E5).

### E3 - Income schedule
The recurring-income definition attached to a holding: what it pays and when. Essential, not optional - it powers the cash-flow view.

- **Parts.** Amount per payout · cadence/frequency (monthly dividend · coupon date · rent · deposit interest) · next date(s) · currency.
- **Spawned by.** **RJ3** ("see what is coming ... across all of them"). It is the rule that **generates** the forward payouts the user actually looks at.
- **Related to.** Belongs to a **Holding** (E1); its shape comes from the **Asset type** (E2); **generates Payouts** (E4).

### E4 - Payout (income event)
One instance of income, projected or realized. The unit the payout calendar and the realized track record are both made of.

- **Parts.** Source holding · amount · currency · date · **status** (projected → realized, auto on the date) · correction via Record changes.
- **Spawned by.** **RJ3** (forward: "what is coming") and **EJ3** (realized: "the income I have actually earned add up"). The status flow is a silent auto-roll: a projected payout becomes realized once its date passes, on the known schedule, with no per-payout confirm. On session start the realized roll is surfaced as a "you got paid" greeting that lists what landed - informing, not gating. The user only intervenes when reality diverged - a payout that did not happen or paid a different amount - through the Record changes flow, with that greeting one natural way in (decision: scheduled payouts auto-roll silently and are surfaced as a greeting, corrections in a dedicated changes flow).
- **Related to.** Generated by an **Income schedule** (E3); belongs to a **Holding** (E1); aggregated into the **Portfolio summary's** blended/forward income (E6).

### E5 - Value snapshot (valuation history)
A recorded value of a holding at a point in time. The real-data basis for the 30-day change and direction.

- **Parts.** Holding · value · currency · as-of timestamp · source (auto-fetched vs user-entered).
- **Spawned by.** **Main job** (position + its direction) and **EJ1** (feel on top, not unsure). For price-tracked holdings the history is auto-fetched; for manually-valued ones the user enters periodic updates, each saved as a snapshot. Direction is shown **only where real snapshots exist**, never fabricated (decision: 30-day change only where real data).
- **Related to.** Accumulates under a **Holding** (E1); feeds the position figure and direction in the **Portfolio summary** (E6); for price-tracked holdings, filled by the price feed (see Under question, U1).

### E6 - Portfolio summary (derived aggregate)
The consolidated whole the user opens Flows to see. **Computed, not stored** - a roll-up of E1/E4/E5, listed as an entity because it is the object the Main job centers on.

- **Parts.** Total position (sum of current values in display currency) · breakdown by asset type · blended this-month income (realized + projected) · upcoming projected income. (How these split into lenses/screens is a later section, not decided here.)
- **Spawned by.** **Main job** ("understand my whole position and what it is paying me") and **EJ1**. The co-equal position + income framing comes straight from the research (§6 move #1: upkeep/consolidation is the named pain, forward income a latent delight).
- **Related to.** Aggregates **Holdings** (E1), **Payouts** (E4), and **Value snapshots** (E5); rendered in the user's **display Currency** (E7).

### E7 - Currency & FX
Multi-currency holdings shown in one chosen display currency, with the native value kept visible. A design theme, not a footnote (Inzhur values in UAH pegged to USD; users also hold other currencies).

- **Parts.** Native currency per holding/payout (a field on E1/E4) · the user's single **display-currency** choice · the **daily FX rate** (auto-fetched) · native + converted shown together.
- **Spawned by.** **Main job** - "whole position" across several currencies is impossible without one display currency; multi-currency clarity is a confirmed beachhead want (research §6: R8, UAH/USD peg). Daily-fetched FX keeps a fresh price from pairing with a stale rate (decision: FX daily, not live-tick).
- **Related to.** A field on **Holding** (E1) and **Payout** (E4); the display choice scales the whole **Portfolio summary** (E6).

### E8 - Import draft & mapping
The bring-over from the user's existing spreadsheet: the column mapping plus the draft rows awaiting review. The bridge that removes Excel switching cost.

- **Parts.** Source file (CSV/sheet now; PDF/image later) · auto-detected header→field mapping · user remap overrides · saveable mapping template · parsed **draft holdings** pending review/confirm before they become real E1 holdings.
- **Spawned by.** **RJ4** ("bring it across without re-entering everything"). Auto-detect + remap is the CSV bridge (decision: CSV = auto-detect + remap). An **optional** AI-assisted variant drafts the mapping from a messy file (needs the BYOK credential, U2).
- **Related to.** Produces **Holdings** (E1); its optional AI path depends on the BYOK LLM credential (U2).

### E9 - Privacy / sharing stance
The control for where the user sits on the privacy↔convenience line. A secondary control for the minority who want it, **not** the reason the default is no-account (that reason is friction, see the guardrail below).

- **Parts.** Per-portion sharing choice (which holdings stay local vs shared) · "never your balances" copy · gates the opt-in **Account / User** (E10) and its sync.
- **Spawned by.** **RJ5** ("choose what stays on my device and what I share") and **EJ2** ("feel my data is mine") - both secondary (P3, thin evidence). Honest caveat from the research: 0% name distrust as the top pain and 50% are comfortable with bank/broker apps, so this is a selectable control and a side-benefit for the ~37% who have abandoned an app over data demands, not a hero and not the driver of the architecture (research §7.3).
- **Related to.** Pairs with the opt-in **Account / User** (E10) as the opposite pole of the same spectrum; governs which **Holdings** (E1) are shared vs local.

### E10 - Account / User (optional identity)
The opt-in identity for a user who chooses the automation end of the spectrum over local-only. It exists **only when the user opts in** - local-first / no-account stays the default, so Flows does not become the cloud-account-by-default tracker it differentiates against.

- **Parts.** A user identity/credential · the sharing scope it carries (which holdings are shared vs kept local, with E9) · one or more **broker sync connections** (e.g. Interactive Brokers) that auto-pull a holdings list · the data sync writes back (new/updated holdings).
- **Spawned by.** **RJ5** - its convenience pole ("opt into broker sync for part of the portfolio while keeping the rest local"; half the surveyed users are comfortable with bank/broker apps). Serves **RJ1** for the syncable subset by bringing those numbers together automatically.
- **Related to.** Opposite pole of the **Privacy / sharing stance** (E9); **auto-creates Holdings** (E1) via sync; gated by the user's stance.
- **Beachhead caveat (from jtbd).** Broker sync reaches no Ukrainian institutions, so for the Inzhur beachhead it closes no reachable job and the UA core (Inzhur + OVDP) is fed by its own feeds, not by sync. Account + sync therefore serve the non-UA long tail and future expansion; they are opt-in and **off the beachhead critical path** - they should not drive the core screens or the usability test. (Open technical question, deliberately unsettled: whether opt-in sync truly needs a server account or can stay a client-side broker connection.)

## Under question

Objects deliberately kept out of the main list - either no in-scope job requires them, a job exists but is explicitly deferred, or their existence is only inferred. Named here so the exclusion is a decision, not an oversight.

- **U1 - Price feed / market-data source `[system]`.** Auto-fetched current price + history for price-tracked assets (keyed on symbol), plus the OVDP/Inzhur feeds. **Why not a main entity:** no job makes the *feed itself* something the user handles - they deal with the resulting value and its "as of" freshness (E5), not the feed object. Infrastructure behind RJ1, not a user-facing entity. The research confirms freshness, not feed coverage, is the trust bar (§7.3).
- **U2 - BYOK LLM credential `[conditional]`.** The user's own LLM key (or on-device model) for AI-assisted import. **Why not main:** it exists only on the optional power path of E8; RJ4 is already matched by competitors and is not an unmet job (jtbd conclusion), so this is in scope but not load-bearing. A sub-part of E8, surfaced only if the user opts into AI import.
- **U3 - AI conversation as one input method `[?] decide at wireframe stage`.** A possible (not necessarily central) way to do some of the work by talking instead of filling forms: add or edit an asset by hand, start an import, or fix a value that got pulled in wrong. It would sit *alongside* direct forms, not replace them. **Why not a main entity.** It is an *interaction model* for mutating E1-E10, not a data object of its own; if a thread is ever kept, the stored object would be a conversation / command history (reusing the BYOK credential, U2). Explicitly a wireframe / detailed-design call, not one to settle now - recorded so the option isn't lost. *(Broker sync, formerly listed here, is now modeled under E10.)*
- **U4 - Language preference (EN↔UA) `[constraint, not a job]`.** The in-UI language toggle. **Why not main:** no jtbd job spawns it. It exists for the validation/portfolio need (Ukrainian for the Inzhur usability tests, English for the case study), a project constraint rather than a user job. Real and in v1 scope, but not entity-of-a-job, so it sits here.
- **U5 - Tag / goal `[thin]`.** A label or a long-term target on a holding (as in FIREkit). **Why not main:** the only job that would need it is HJ3 ("track progress toward a long-term goal"), which now has thin support: one survey respondent directly asked for a contribution-to-goal calculator (R26), another for past/future interpolation (R23). That is enough to add a complementary **Goals** screen and an **Analytics** screen (below), but not to promote a per-holding goal/tag as a core entity, so the field stays here until testing gives it more weight.

**Default guardrail.** No-account quick start stays the **default** - chosen for low onboarding friction (instant value, no sign-up wall) and because the upkeep-killing feeds for the beachhead (Inzhur + OVDP, via E5/E7) work with or without an account, **not** as a privacy stance: our own data says trust is a minor entry filter, not a driver. The **Account / User** (E10) is opt-in for automation, cross-device, and durability, never assumed.

## Screens (draft)

Derived from the **Entities** above and the jobs in [`jtbd.md`](../research/jtbd.md), grouped by what the person is trying to do - not by competitor navigation or "site sections." Each screen names the job it serves (linked to jtbd.md); a screen with no job is flagged `[СИРОТА]`. Persona need is marked `[P1]` (primary - Excel Consolidator) or `[P3]` (secondary). **Empty / first-run / error are states of a screen, not screens**, so they are not listed as nodes. Depth is deliberately shallow here - sub-levels and the flow between screens come next.

**A. See where I stand** *(the consolidated whole - E6)*
- **Overview (consolidated dashboard)** `[P1]` - the position lens: total position across everything + breakdown by asset type, with a blended this-month income headline so income stays co-equal on the front door. (Main, EJ1 · [jtbd.md](../research/jtbd.md))
  - the two co-equal leads, position and income, are delivered as two peer screens rather than one toggle: position lives here, the month-by-month income/time view is the **Calendar** screen below. The income headline stays on Overview; the full view is one tap away.
  - *first-run / nothing-added-yet is an empty **state** of this screen, not a separate screen.*
  - *a session-open "income arrived while you were away" greeting is another **state** of this screen (it surfaces the silent auto-roll and offers a jump into Record changes), not a screen.*
- **Calendar** `[P1]` - a month-view of every dated money event: this month's blended income, navigable to past and future months. Past months show realized income; future months show projected income, labeled "projected" so a forecast is never read as an exact figure. It also plots the dated changes the user recorded - buys/sells that came from import or from Record changes - with income as the lead layer. This is the "focus on income alone" screen. (Main, RJ1, RJ3, EJ1, EJ3 · [jtbd.md](../research/jtbd.md))
  - *month view only: one month at a time, navigable back and forward, not an infinite ledger.*

*Derived views (computed on the held data, no new entry):*
- **Analytics** `[P1]` - insights over the real holdings: allocation/diversification by asset type and currency, income by source, P&L (unrealized + total return) over time, historical trends. Nothing is fabricated - it all computes from holdings (E1) + value snapshots (E5). This is where P&L gets a real home, kept off the Overview hero on purpose. (EJ1, EJ3 · thin: a survey ask for past/future interpolation, R23 · [jtbd.md](../research/jtbd.md))
- **Goals / Calculator** `[P1]` - a contribution-to-goal scenario tool: "how much to contribute per month to reach target X," with defaults drawn from the user's own history (average monthly contribution, current payouts) and editable parameters. It is **labeled an estimate, never a promise** - the same trust rule as the Calendar's "projected" tag, so a model-based projection is never shown as fact. (EJ3 · thin: a direct survey request, R26; the long-term-goal hypothesis HJ3 · [jtbd.md](../research/jtbd.md))
  - *Both are complementary, evidence-thin screens (single survey voices, R23/R26): nav-promoted for the portfolio's range, but they do not claim the core jobs, which Overview, Calendar, and Record changes already close.*

**B. Work with my holdings** *(E1, and correcting E4)*
- **Holding detail** `[P1]` - one asset's full picture: value + history, income schedule, custom fields. (RJ2 · [jtbd.md](../research/jtbd.md))
  - P&L (unrealized + total return) is a minimal **section** here, with no job of its own - kept off the dashboard hero on purpose, so it is not its own screen.
- **Record changes** `[P1]` - the persistent "Make changes" entry on Overview and Holding detail (and reached straight from the "you got paid" greeting when a surfaced payout is wrong): pick scope (one / several / all) and what changed (bought more, sold, a value correction, a payout that did or did not land); the options shown depend on the asset type. Routes to the manual form in edit mode or the payout-edit screen, in bulk or per holding. Scheduled payouts auto-roll to realized on their own, so this is the safety valve for what the feeds and schedules can't see. (Main, RJ2, EJ3 · [jtbd.md](../research/jtbd.md))
- **Payout edit** `[P1]` - correct one realized payout that diverged from its schedule (did not happen, or a different amount). Reached from the Record changes flow, not a per-payout confirm: scheduled payouts roll to realized automatically. (EJ3 · [jtbd.md](../research/jtbd.md))

**C. Get holdings in** *(creating E1)*
- **Get started (onboarding)** `[P1]` - first-run only: before any empty state, proactively offers the on-ramps (import / connect / add manually / skip) so a new user does not land on a blank dashboard. No login needed; routes into the same screens below. (RJ1, RJ2, RJ4 · [jtbd.md](../research/jtbd.md))
- **Add a holding** `[P1]` - the single entry point: pick *what* to add, then *how*. (RJ2 · [jtbd.md](../research/jtbd.md))
  - **Add manually** `[P1]` - typed stub per asset type + custom-field escape hatch. (RJ2)
  - **Import from a spreadsheet** `[P1]` - the bridge from Excel: pick/drop a file, auto-detect headers. (RJ4)
    - **Map columns (remap)** `[P1]` - fix header→field mismatches the auto-detect missed. (RJ4)
    - **Review draft holdings** `[P1]` - check the parsed draft rows before they become real holdings; fix or skip bad rows. (RJ4)
  - **Connect an account / broker sync** `[P3]` - opt-in via E10, off the beachhead critical path (no UA reach). (RJ1)

**D. Control my data & privacy** *(E9, E10)*
- **My data & privacy** `[P3]` - sharing stance (local vs shared), manage connected accounts, export / backup. (RJ5, EJ2 · [jtbd.md](../research/jtbd.md))

**Global header** *(chrome present on every screen, not a screen)*
- The **display-currency switch** (one chosen display currency; the multi-currency-clarity need behind seeing a single total - Main) and the **language toggle EN↔UA** (English for the portfolio, Ukrainian for the Inzhur usability tests) both live in a persistent header on every screen, reachable in one tap from anywhere. Because they are always-present chrome, neither is a standalone screen - so neither is listed as a node here nor as a column in the coverage matrix. This is what resolves the former Language screen-orphan and the borderline Display-currency screen: they were never really destinations, they are controls.

### Primary vs secondary at a glance
- **P1 critical path (primary):** A (Overview + Calendar) → C (add / import) → B (holding detail), with the display-currency switch in the global header. This is the spine the usability test runs on.
- **Secondary (P3):** D (my data & privacy) and the *connect account / sync* option in C - real but off the beachhead critical path.
- **P2 (low-complexity, mostly out of scope):** drives no unique screen; the outgrowing subset uses the same P1 core (dashboard + add). Noted so its absence is a decision, not a gap.

## Navigation

How a person moves through the screens above. Built from the job-clusters, not from a default app chrome.

### 1. Global navigation - 4 entries

| Entry | Job cluster it opens | Why it earns an always-visible slot |
|---|---|---|
| **Overview** | Main, EJ1 ([jtbd.md](../research/jtbd.md)) | The whole reason the product exists: the consolidated position + income. Cluster A. |
| **Calendar** | RJ3, EJ3 ([jtbd.md](../research/jtbd.md)) | The income lead, delivered as a month-view calendar: this month's blended income, navigable back to realized months and forward to projected ones (future labeled "projected"). A user can focus on income alone here, so it earns a peer entry rather than a buried tab. |
| **Analytics** | EJ1, EJ3 ([jtbd.md](../research/jtbd.md)) | A recurring "how am I doing" view: allocation, income by source, P&L and trends over time, all derived from the held data. Complementary and evidence-thin (R23), promoted to a tab for the portfolio's range. |
| **Goals** | EJ3 ([jtbd.md](../research/jtbd.md)) | A recurring "am I on track" view: the contribution-to-goal calculator. Complementary and evidence-thin (R26 / HJ3); a clearly-labeled scenario tool, not a promise. |

**Add (+) is not a nav entry.** Adding holdings is occasional, not a recurring destination, so the create action (manual / import / connect) lives **on the Overview / Assets screen**, not in the global nav. One "+" reveals what to add, then how.

**Profile is a header entry point, not a tab.** A persistent profile affordance in the global header opens the account surface - create a profile, log in, or manage it - reachable any time. It is the entry to the opt-in Account/User (E10) and to My data & privacy, both off the beachhead critical path; the local-first default means a user can do everything without ever opening it.

**No Settings tab.** Display currency and the EN↔UA language toggle do not need one: they live in a **global header** present on every screen, one tap from anywhere. My data & privacy is P3/secondary and sits behind the profile affordance, counting as **deep**. A standing "Settings" tab would be there *because every app has one*, which is exactly the reasoning we are rejecting.

*This gives Position (carried on Overview) and the Calendar (the income/time view) peer billing in the nav itself. It settles the earlier open "one screen with a toggle vs two screens" lens question in favour of two peer screens over one shared holdings base.*

### 2. Depth to the main job (tap count)

> **Main job:** *"...understand my whole position and what it is paying me, faster than my spreadsheet..."*

- Launch lands directly on **Overview**.
- Overview is a summary-first cascade (the chosen consolidated-view pattern): the hero carries **total position + blended this-month income, co-equal**, then the by-type breakdown, then an embedded payout-calendar module.
- So the headline of the main job - whole position *and* what it pays - sits on the landing screen.

**Taps from first screen to the main job = 0** for a returning P1.

Cross-checks, all within budget:
- Full income calendar / "focus on income alone" = **1 tap** (Calendar).
- Analytics (allocation, P&L, trends) and Goals (the calculator) = **1 tap** each (their nav tabs).
- A single holding's detail = **1 tap** (tap a holding in the breakdown).
- Add or import a holding = **1 tap** (the + action on Overview).
- Record a change (bought/sold, a missed payout) = **1 tap** (the Make changes action on Overview).

**First-run caveat (honest):** the very first session has no holdings, so instead of dropping the user on Overview's *empty state* it routes through **Get started (onboarding)**, which offers the on-ramps (import / connect / add manually) up front - that is RJ4/RJ2/RJ1 (*getting in*), a precondition, not the main job itself. From the second session on, every open is 0 taps. P1 checks weekly or more (survey Q6), so the recurring 0-tap path is the one that counts.

**Result: 0 ≤ 3, so no restructuring is needed.** The structure already puts the main job on the front door; the budget would only bind if the consolidated view were demoted behind a menu, which it is not.

### 3. Global / contextual / deep

- **Global (always visible)** - the 4 nav entries: **Overview**, **Calendar**, **Analytics**, **Goals**. The first two are recurring P1 jobs (review, cash-flow); the last two are complementary "how am I doing / am I on track" views, promoted to tabs for the portfolio's range.
- **Global header (persistent chrome on every screen):**
  - **Display-currency switch** - change the single display currency from anywhere (Main; multi-currency clarity).
  - **Language toggle EN↔UA** - flips the whole UI; English for the portfolio, Ukrainian for the Inzhur tests. A utility control, not a job tab.
  - **Profile** - opens the account surface (create / log in / manage); the entry to the opt-in Account/User and My data & privacy. Local-first means it is optional.
- **Contextual (appears inside a flow, not in the chrome):**
  - **Add (+)** - the create action (manual / import / connect) on the Overview / Assets screen; occasional, so not a nav tab.
  - **Holding detail** - reached by tapping a holding in Overview's breakdown.
  - **Record changes** - a persistent "Make changes" action on Overview (act on all holdings, several, or pick one) and on Holding detail (that one holding, pre-scoped). The correction path for what automation can't see; scheduled payouts roll to realized on their own, so this is not shown per payout.
  - **Payout edit** - a leaf of Record changes: opens only to correct one realized payout that diverged (did not happen, or a different amount). Not a recurring confirm prompt.
  - **Import detect → remap → review** - steps inside the Add → Import flow.
  - **The what/how branch + typed-stub form** - inside Add.
  - **Connect an account / broker sync** - an option offered inside Add (and managed behind the profile affordance).
- **First-run gate (neither global nav nor deep):**
  - **Get started (onboarding)** - shown once on the first launch with no holdings, then never again; it is a gate into the add/import/connect on-ramps, not a screen in the chrome.
- **Deep (rare actions, behind the profile affordance):**
  - **My data & privacy** - sharing stance, manage connected accounts, export/backup (RJ5/EJ2; P3, secondary).

### Defect list 1 - screen-orphans (a column with no `✓`: a screen no job needs)

- **None.** The earlier screen-orphan (Language EN↔UA) and the borderline single-`✓` Display currency are no longer screens: both became persistent **global-header** controls. They leave the screen inventory entirely rather than sitting as a job-less column (LANG) or a thinly-justified one (CUR). Every remaining column carries at least one `✓`.

### Defect list 2 - job-orphans (a row with no `✓`: a job no screen closes)

- **None.** Every job maps to at least one screen, so there is no outright product hole - no job where the user would have nowhere to go. That is the result we want, not a free pass to stop looking. Three rows are *thin* and worth watching before wireframes, with resolutions:
  - **EJ2 (feel my data is mine) rests on a single screen (DATA).** Thin but not orphaned. **Resolution: keep, watch.** If usability testing shows the ownership feeling needs reinforcing earlier, add honest "never your balances" cues as *states* on DASH/first-run (states, not new screens) - backlog, not now.
  - **RJ5's per-holding sharing choice has no per-holding control.** RJ5 is closed at the portfolio level (DATA + CONN), but "which holdings stay local vs shared" has no control on HD. **Resolution: backlog.** Add a per-holding sharing toggle to Holding detail only if per-portion sharing proves real in testing; today the portfolio-level control is enough and broker sync is off the beachhead path anyway.
  - **RJ1 is screen-light by design.** It is closed mostly by background automation (Inzhur/OVDP feeds, prices, daily FX) surfacing fresh on DASH; the on-ramp screens (ONB onboarding, CONN connect) only pull the sources in. **Resolution: keep, no new screen.** The job's closure depends on the feeds, not a UI - so the thing to protect is the "as of" freshness *state* on DASH, not another screen. Flagged so "few screens" is not mistaken for "under-served."
